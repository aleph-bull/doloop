# Post videos and pictures on Cloudflare R2

Set up 2026-10-21. Without R2 the API keeps every post's file in Postgres as base64 and
sends it back through Render on every play. Neon's free plan holds about 150 videos that
way, and Render's free plan has 5 GB of outbound traffic a month for the whole app, about
1,000 plays, after which Render suspends the API until the next month (or bills $0.15/GB
with a card on file). R2 stores files for $0.015/GB a month with the first 10 GB free, and
never charges for downloads.

## How it works

1. The portal asks the API for an upload link: `POST /api/social/uploads` with the file's
   type and size. The API checks them (video up to 40 MB, picture up to 2 MB, 30 links an
   hour per person) and signs a `PUT` link to `uploads/<user id>/<uuid>` that is good for 15
   minutes. The signature covers the type and the exact size, so the link takes only that
   file.
2. The browser uploads straight to R2 through that link (with a progress percentage on the
   Post button). The file never passes through Render.
3. The post is made with `upload: <key>`. The API looks at what arrived (`HEAD`), checks it
   again, copies it inside the bucket to `posts/<user id>/<uuid>.<ext>` and saves the key in
   `post_media.key` (`data` stays empty).
4. To show it, the portal asks `GET /api/posts/:id/media/url` and gets a link that is good
   for an hour, used as a plain `<img src>` / `<video src>`. Playing never touches Render
   either. The same visibility rule as the feed applies: a post kept to friends gives no
   link to anyone else.
5. Deleting a post deletes its file. Deleting an account deletes all of its files.
   Anything left under `uploads/` (an upload whose post was never made) is removed by the
   bucket's lifecycle rule after a day.

Without the `R2_*` variables nothing changes from before: files go with the post as data
URLs, videos stay capped at 5 MB, and `GET /api/social/uploads` says `direct: false` so the
portal knows. Posts made before R2 keep their bytes in Postgres and still play. A portal
tab from before this change still works too: it sends files inline and fetches the bytes
from `GET /api/posts/:id/media`, which passes R2 files through.

**Too big?** The composer and the timelapse's "Share to Social" no longer refuse a file
over the limit. They say how big it is and offer to compress it: videos are re-encoded in
the browser with WebCodecs (mediabunny, loaded only then) at a bitrate worked out from the
length, smaller and at 30 fps if needed, trying once more if the encoder overshoots;
pictures are redrawn as JPEG. A video too long to fit even at a low bitrate is refused with
"A shorter clip would."

The code: `apps/api/src/services/media-store.ts` (the R2 client, aws4fetch),
`apps/api/src/routes/social.ts`, `apps/portal/src/lib/post-media.ts` (`sendMedia`),
`apps/portal/src/lib/compress.ts`, `components/social/CompressOffer.tsx`. Tests:
`apps/api/src/test/social-media.test.ts`.

## Setting it up

Everything here is free on R2's free tier. Keep the four values from step 4 out of the repo
and out of chats: they go only in Render and in your local `apps/api/.env`.

1. **Turn R2 on.** In the Cloudflare dashboard (the account komogon.app's DNS is already
   on), open **Storage & databases → R2 → Overview** and go through the checkout to add
   the R2 subscription. It is the free plan with usage billing; Cloudflare may ask for a
   card even though nothing is charged under the free amounts.
2. **Make the bucket.** **Create bucket**, name it `komodon-media`, location Automatic,
   default storage class Standard (the free tier doesn't cover Infrequent Access). Leave
   public access off: everything goes through signed links.
3. **Bucket settings** (open the bucket, then **Settings**):
   - **CORS policy → Add CORS policy**, JSON tab, paste this and save. The portal runs on
     **www.komogon.app** (komogon.app redirects there); with only `https://komogon.app`
     listed, every upload failed with "The upload didn't go through" (2026-10-21). Add any
     other address the portal is opened at (the `*.vercel.app` one):

     ```json
     [
       {
         "AllowedOrigins": ["https://www.komogon.app", "https://komogon.app"],
         "AllowedMethods": ["PUT", "GET"],
         "AllowedHeaders": ["content-type"],
         "ExposeHeaders": ["ETag"],
         "MaxAgeSeconds": 3600
       }
     ]
     ```

   - **Object lifecycle rules → Add rule**: name it "Unposted uploads", prefix
     `uploads/`, delete objects 1 day after they were uploaded. Save.
4. **An API token.** Back on **R2 → Overview**, under **Account Details**, **Manage** next
   to **API Tokens** → **Create Account API token**. Permission **Object Read & Write**,
   applied to the `komodon-media` bucket only, no expiry. Create it, then copy the **Access
   Key ID** and **Secret Access Key** (the secret is shown once). The **Account ID** is
   under Account Details on the Overview page.
5. **Check it from this PC** before touching Render. Put the four values in
   `apps/api/.env` (gitignored):

   ```
   R2_ACCOUNT_ID=...
   R2_ACCESS_KEY_ID=...
   R2_SECRET_ACCESS_KEY=...
   R2_BUCKET=komodon-media
   ```

   and run `node scripts/r2-check.mjs https://www.komogon.app`. It uploads a small file
   through a signed link, checks that a link refuses a file of another size, reads it back,
   copies it, deletes both and checks the CORS policy for that address. It ends with
   "R2 is ready." or says what is off. Take the four lines back out of `apps/api/.env`
   afterwards if you don't want local sandboxes to use the real bucket.

6. **Render.** In the `komogon-api` service, **Environment**, add the same four variables
   (`render.yaml` lists them, `sync: false`). Saving restarts the API; its log says
   "R2 not set up" when any of them is missing.
7. **Deploy** (pushed to main 2026-10-21). The migration `0023_post_media_r2` makes
   `post_media.data` nullable and adds `post_media.key`; it runs on start-up.

If the bucket is created in the EU jurisdiction, also set
`R2_ENDPOINT=https://<account id>.eu.r2.cloudflarestorage.com`.

## Trying it locally without an account

A stand-in for R2 that checks signatures the way R2 does was used to test this branch (the
`r2-sandbox` launch configs, 8832/5232, with `R2_ENDPOINT=http://127.0.0.1:8834`). It isn't
in the repo; any S3-compatible server on that address works the same way.
